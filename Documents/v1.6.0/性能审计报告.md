# 🚀 性能审计报告 v1.6.0

> 审计日期：2026/09/18
> 分支：`refactor/v1.6.0`
> 审计范围：`electron/`（当前桌面端主入口）、`server/`、`drivers/`、`core/`、`utils/`、构建 / 打包链路
> 已排除：`node_modules`、`.git`、`dist` 产物代码、已废弃的 `app`（JavaFX）模块
> 基线包含审计时工作区未提交的改动（ResultGrid / RpcServer 等）
> 说明：本报告只做审计，未修改任何代码

## 一、结论摘要

在 2019 款 Intel Mac 上卡顿的根因不是单一问题，而是四类叠加：

1. **渲染层：零渲染隔离**。`App.tsx` 单组件持有全部状态，全项目 **0 个 `React.memo` / `useCallback` / Context**
   （已核实）。任何状态变化（敲键盘、查询进度事件、拖选单元格）都会重渲染整棵组件树，包括结果表格、对象树、日志、菜单。
2. **数据量无边界**。查询结果集端到端不设上限，且**每次单元格编辑都把整份结果集重新 JSON 序列化后经 IPC 回传**；日志最多
   8192 条且不虚拟化。
3. **启动串行 + 体积大**。开发态每次都跑完整 `vite build`；打包态窗口创建在 JVM 启动之后才进行；4MB 主 bundle 在首屏一次性解析。
4. **Java 侧资源泄漏**。`resultCache`、`Driver.taskQueue`、PostgreSQL 分库连接池均无回收上限，长时间会话内存持续上涨。

## 四、P2 级问题（体积 / 内存 / 健壮性）

- 依赖臃肿：`valkyrie-server.jar` 47MB，含 POI ~31MB、sqlite 原生库 ~21MB、JMH（基准测试库，jsqlparser 传递依赖）~5MB、Jackson ~
  5.4MB（服务端实际未用，走 fastjson2）、旧版 fastjson 兼容包。`server/pom.xml:53-90` 无 `artifactSet` 排除、无 `minimizeJar`。
- `RUNTIME_MODULES` 保留了疑似未用的 `java.net.http`、`java.scripting`、`java.management`（`package.cjs:38-53`），jlink 产物偏大。
- `GridRow` 未预分配容量；`getRowValue` 每次调用分配 lambda（`QueryResult.java:498-501`）。
- Redis 单例 `Jedis` 被多线程共享（`RedisDataSource.java:24-33`），非线程安全。
- SQLite N+1：建表列表每表 `COUNT(*)` + `dbstat`，每索引一次 `PRAGMA index_info`（`SQLiteDriver.java:118-127,188-202`）。
- 启动时 `osascript` 枚举系统字体约 **0.5s**，与 JVM 启动争抢 CPU，但字体下拉打开前并不需要（`main.tsx:13` →
  `settings.ts:126`）。
- 根目录遗留 214MB JavaFX 版 jlink runtime 和 183MB 旧 dmg（`build/`），不参与新流程但占空间、易混淆。

## 五、优化后性能预计提升

> 基于 2019 款 Intel Mac（i5/i7、8–16GB、无独显）估算，含审计实测的 JVM 启动数据。为区间估计，非 SLA。

### 1. 冷启动（打包版，到可交互）

| 手段                                     | 预计节省                                      |
|----------------------------------------|-------------------------------------------|
| 窗口创建与 JVM 启动并行（P1-11）                  | 300–800 ms                                |
| Monaco 按需加载 + 组件 lazy + 代码分割（P0-6, P2） | 300–800 ms                                |
| AppCDS / jlink CDS（P1-11）              | 190–380 ms                                |
| jlink 模块瘦身（P2）                         | 体积约 5–10MB（启动收益小）                         |
| **合计**                                 | **约 0.8–2.0 s（当前冷启动约 3–4s → 约 1.5–2.5s）** |

### 2. 开发启动（`start.cjs`）

| 手段                        | 预计节省                     |
|---------------------------|--------------------------|
| 跳过无改动的 `vite build`（P0-9） | **8–30 s / 次**（无改动时几乎瞬时） |

### 3. 运行时交互

| 场景（大结果 / 大数据量）    | 当前                | 优化后                  | 提升            |
|-------------------|-------------------|----------------------|---------------|
| 编辑器输入（有结果表 / 日志时） | 每键 50–300ms 掉帧    | <5ms                 | **10–50×**    |
| 结果表拖拽框选（10 万行）    | 每次移动几十 ms + 全树重渲染 | <1ms                 | **数十倍**       |
| 日志（数千条）事件刷新       | 数百 ms 全量重建        | <16ms 虚拟化            | **10×+**      |
| 对象树过滤（上万节点）       | O(N²)，秒级卡死        | O(N)，毫秒级             | **数量级**       |
| 单单元格编辑（10 万行结果）   | 全量回传，数百 MB IPC    | 仅回传变更行，数据量降 **>99%** | 交互从秒级→毫秒      |
| 大结果首次返回           | 全量物化 + 全量 JSON 一行 | 分页 / 流式              | 内存降 80%+，首屏更快 |

### 4. 稳定性 / 内存（长时间运行）

- 修复 P0-10（结果缓存上限、`taskQueue` 回收、PG 连接池复用）：长会话内存不再持续增长，消除卡顿累积与 OOM 风险。
- XLSX 改流式：大表导出内存峰值可降 **一个数量级**。

### 5. 安装包体积

| 项             | 现状      | 预计                                                         |
|---------------|---------|------------------------------------------------------------|
| 主 JS bundle   | 4.08 MB | **<1 MB**（仅 SQL 语言）                                        |
| server jar    | 47 MB   | **约 25–30 MB**（剔除 JMH/Jackson/旧 fastjson、按平台过滤 sqlite 原生库） |
| jlink runtime | ~47 MB  | 可减数 MB                                                     |

## 六、建议实施顺序（按性价比）

### 第一批（改动小、收益最大）

1. `start.cjs` 增加 `dist/renderer` 新鲜度判断，跳过无改动 vite build。
2. 结果集与日志的虚拟化补强 + 日志按可见性懒重建。
3. 菜单 `buildAppMenus` / stringify 用 `useMemo` 收敛；`React.memo` + `useCallback` 给 ResultGrid / Tree / LogConsole /
   Toolbar 加渲染隔离。
4. 进度事件在渲染层做 rAF 合并。

### 第二批（需要小重构）

5. Monaco 改为 `monaco-editor/esm/vs/editor/editor.api` + 仅 SQL contribution，并对对话框做 `React.lazy`。
6. 窗口创建与 JVM 启动并行；jlink 加 `--generate-cds-archive`；JVM 加 AppCDS 与 `-Djava.awt.headless=true`。
7. Java：`taskQueue` 在 `finally` 中 `remove`；`resultCache` 加 LRU / 大小上限；PG 连接池复用与关闭；`StatementProxy` 日志降为
   DEBUG。

### 第三批（数据链路改造）

8. 查询结果分页 / 流式 + 单元格编辑增量返回（只回传变更行）。
9. JDBC `setFetchSize` / `setMaxRows` / `setQueryTimeout` + 元数据缓存。
10. XLSX 改 `SXSSFWorkbook` / 流式；导出正则预编译；依赖瘦身。

## 七、已确认做得好的地方（勿动）

- `ResultGrid` 已有行虚拟化 + 单 rAF 滚动合并（`ResultGrid.tsx:284-310,492-505,726-732`）。
- Monaco 编辑器实例只创建一次并跨标签常驻，无模型泄漏（`useMonacoEditor.ts:52-266`）。
- IPC 事件订阅均有正确的取消订阅，无泄漏。
- Java 服务端无 Spring / 无类路径扫描，启动本身轻量（约 0.5s，主要是类加载）。
